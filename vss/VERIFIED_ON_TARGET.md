# Verified on target

What was actually run on real hardware, and what is still a stand-in. Nothing in this file
is projected or expected behaviour.

## The hardware and software

| | |
|---|---|
| Target | Raspberry Pi Compute Module 4 |
| OS | QNX 8.0 (QNX Everywhere image), aarch64le |
| Signal service | QPP (QNX POSIX Publish Subscribe), `main`, QPP_VERSION 1.1.0, built from the QNX GitHub repo with SDP 8.0 |
| Catalog | `catalog/qpp_catalog_airquality_demo.json`, generated by `catalog/make_qpp_catalog.py` from a vss-tools master export of VSS + the overlay in `proposal/overlay/` |
| Sensor device | A Teensy 4.0 running the I²C slave sketch in `../driver/teensy_aq_i2c_slave/` |
| Bus | `/dev/i2c1` (the Pi's header I²C, GPIO2/GPIO3), slave address `0x28`, as configured in [`../configs/aq_i2c.conf`](../configs/aq_i2c.conf). Wiring is in the [Teensy sketch README](../driver/teensy_aq_i2c_slave/README.md) |
| Host link | A direct ethernet cable, with the target driven over `qconn` |

## What ran

**The bus works.** An I²C scan found the device acknowledging at `0x28` on `/dev/i2c1`,
with nothing on `/dev/i2c0`. Note that the QNX Raspberry Pi image does not mux the header
I²C pins at boot, so `/dev/i2c1` is dead until `gpio-bcm2711 set 2 a0 pu` and
`gpio-bcm2711 set 3 a0 pu` have been run. `../scripts/demo.sh mux` does exactly that.

**The catalog loads.** QPP started in signal-service mode against the air-quality catalog
and materialised all 17 signals under the mount point, plus their metadata siblings and the
one `?control` channel for the `IsRecirculationActive` actuator. Reading
`.PM25.metadata` returned the proposed VSS definition, including `"unit":"ug/m^3"` and the
description, served back by a QNX resource manager.

**Both connector shapes ran, on separate occasions.**

1. `connector/aq_signal_connector.c`, the bridge: air-quality driver → QNX Sensor Framework
   → connector → signal files. Run first against the driver's software simulator bus, then
   against the physical I²C device.
2. `connector/aq_signal_publisher.c`, the direct path: I²C device → signal files, with no
   Sensor Framework in the process at all. During this run the sensor service was never
   started and `/dev/sensor` did not exist, which is what makes the claim checkable rather
   than merely asserted.

## The measured values

The demo scenario is a cabin-filter alert: clean air, then a particulate rise, then a
return to baseline. Driving the sensor emulator through that cycle and reading PM2.5 back
out of the signal file with `cat`, on the direct path:

```
pollute:    22  ->  69  ->  114  ->  150  ->  151    (ramp at its cap)
clear:     153  -> 120  ->   83  ->   48  ->    6
baseline:  6 to 9, wandering
```

Units are µg/m³. Sampling was a few seconds apart, so these are the values a consumer
actually saw, not an interpolation. A binary read of the same file with `od -t f4` agreed
with the text read, confirming the 4-byte float on-disk format the catalog specifies.

The other channels published at the same time, read from their own signal files:

```
PM1 = 6.0   PM10 = 13.0   CO2 = 500.0   NO2 = 0.0
Cabin/HVAC/AmbientAirTemperature = 21.3
```

The bridged connector produced the same shape of result on an earlier run, reaching a peak
of 155 µg/m³ before clearing back to baseline.

## Failure handling, deliberately provoked

The QPP restart case was tested rather than assumed. With the publisher running, `qpp` was
killed outright (confirmed: the process was gone and the mount point no longer existed),
left down for several seconds, and then restarted.

- The publisher kept reading I²C at 1 Hz throughout, unaffected.
- Each signal logged its write failure **once**, as `Bad file descriptor`, and then went
  quiet. Six lines total for the whole outage, not six per second. This is what the error
  rate limiting is for: an embedded target where a chatty failure loop can itself become
  the outage.
- When QPP came back, each signal re-opened and logged `recovered`, and live values were
  flowing again within one sample period, with no operator action.

Clean shutdown was checked the same way: `SIGTERM` produced `publisher: shutting down` and
the process exited with its descriptors closed, rather than being killed mid-write.

## What is real and what is a stand-in

**Real:** the I²C bus, the QNX driver, the Sensor Framework path, both connectors, the QPP
signal service, the catalog, and every value above. The data genuinely travelled from a
physical device on a hardware bus into VSS-named signal files, and was read back out with
ordinary POSIX calls.

**A stand-in:** the device on the bus is a Teensy 4.0 running an emulator sketch, not a
production air-quality sensor part. It speaks the same 18-byte block a real part would be
made to speak, so everything above the wire is unchanged, but the numbers it reports are
generated rather than measured. Swapping in a real part means implementing one bus-read
function.

One honest detail worth stating: the emulator sends an all-zero NO2 channel with its valid
bit set, so `NO2` reads `0.0`. That is a real read of a real zero on the wire, not a
measurement of clean air.

## Known limitations seen during these runs

- The bridged connector binds to one sensor-service instance. If the sensor service is
  restarted underneath it, published values freeze at their last value until the connector
  is restarted. This was observed, not predicted.
- The direct publisher recovers from a QPP restart within one sample period, as shown
  above. It re-opens the I²C bus after five consecutive read failures and keeps retrying
  indefinitely rather than exiting.
- Nothing in this path carries a timestamp. QPP signal metadata holds the datatype,
  description, unit and range, not a last-updated time, and neither program adds one. A
  consumer cannot tell a fresh value from a stale one by reading the signal alone. If that
  matters, publish a companion signal carrying the sample time.
